1장. SEMI E164 (EDA Common Metadata) 개요

SEMI E164는 E120과 E125로 장비 데이터를 모델링할 때, 제조사(Vendor) 마음대로 이름과 구조를 짓지 못하도록 표준화된 작명 규칙(Naming Convention)과 메타데이터 구조를 강제하는 규약입니다. 서로 다른 장비 벤더들이 동일한 형식으로 데이터를 제공하게 만들어, 반도체 제조사의 데이터 통합 비용을 줄이는 것이 핵심 목표입니다.

2장. 도입 배경: 왜 E164가 필요한가?

E120/E125만 적용했을 때의 문제점은 '방언(Dialect)'이 생긴다는 것입니다. A회사의 장비는 온도를 "ChamberTemp"라고 명명하고 섭씨(C)로 주고, B회사의 장비는 "Module_T"라고 명명하고 화씨(F)로 주면 호스트 시스템(FDC, APC)은 각 장비마다 데이터를 변환하는 번역기 코드를 일일이 짜야 했습니다.

E164는 기존의 주요 SECS/GEM 표준(E39, E40, E87, E90, E94, E116 등)에 나오는 상태 모델과 변수 이름들을 Interface A의 표준 모델 노드 이름과 데이터 타입으로 1:1 매핑하여 고정(Hard-coding)합니다.

3장. E164 적용 시의 변화 (Standardization)

1. 일관된 계층 구조 (Consistent Hierarchy)

모든 장비의 Load Port, Process Chamber 등의 모듈 이름이 규격화됩니다. 클라이언트 코드는 장비 벤더가 누구든 상관없이 Equipment.ProcessModule_1.Temperature 와 같은 일관된 XPath(경로)로 센서에 접근할 수 있습니다.

2. 표준화된 상태 머신 (Standardized State Machines)

E90(Substrate Tracking), E87(Carrier Management) 등의 상태 전이 이벤트 이름이 통일됩니다. 예를 들어 웨이퍼가 도착했을 때의 이벤트는 어떤 장비든 CarrierArrived라는 동일한 이벤트명으로 수집됩니다.

3. 호환성 검증 (Compliance Testing)

SEMI는 장비가 E164를 제대로 준수했는지 자동으로 검사할 수 있는 XML 스키마(XSD)를 제공합니다. 장비가 납품될 때 호스트는 이 스키마로 모델을 스캔하여 명명 규칙을 어겼는지 손쉽게 검수할 수 있습니다.

4장. 실무 적용 및 트러블슈팅

표준 파라미터 vs 벤더 고유 파라미터 E164는 '모두가 공통으로 써야 할 기초 정보'만 표준화합니다. 특정 벤더만 가진 특수한 플라즈마 센서나 신기술 파라미터는 여전히 벤더 고유의 이름으로 확장(Extension) 노드 아래에 달리게 됩니다. 따라서 호스트 개발자는 표준 트리와 벤더 종속 트리를 분리해서 수집/분석하는 유연성을 갖춰야 합니다.
버전 간 호환성 문제 E164 표준 자체가 개정되면서 (Freeze 1, Freeze 2 등) 구조가 약간씩 바뀝니다. 구형 장비와 최신 장비가 섞여 있는 팹에서는 여러 버전의 E164 모델 스키마를 동시에 지원하는 Data Broker 시스템이 필요합니다.
