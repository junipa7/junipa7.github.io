SEMI E160 - Data Quality

장비 데이터 품질 표현과 전달. SEMI E160은 장비 데이터가 정상인지, 의심스러운지, 결측인지, 시간적으로 지연됐는지 같은 품질 정보를 함께 전달하는 관점을 다룹니다. 값 자체뿐 아니라 그 값을 믿어도 되는지 알려주는 표준입니다.

학습 목표

이 문서는 수업과 시스템 설계를 돕기 위한 교육용 해설입니다. 실제 프로젝트 적용 시에는 고객 사양서, 장비 벤더 매뉴얼, 최신 SEMI 공식 문서를 함께 확인해야 합니다.

수업에서 기억할 핵심: E160는 FDC, APC, AI 모델, KPI 계산에서 잘못된 센서값이나 결측 데이터를 그대로 사용하지 않도록 품질 코드를 함께 관리할 때 필요합니다. 이 문서를 읽을 때는 표준 번호를 외우는 것보다, 입력 데이터가 어디서 오고 어떤 상태 판단을 거쳐 어떤 업무 시스템으로 전달되는지 따라가야 합니다.

1. 표준의 역할과 현장 배경

SEMI E160은 장비 데이터가 정상인지, 의심스러운지, 결측인지, 시간적으로 지연됐는지 같은 품질 정보를 함께 전달하는 관점을 다룹니다. 값 자체뿐 아니라 그 값을 믿어도 되는지 알려주는 표준입니다.

반도체 fab의 자동화 시스템은 장비, EAP, MES, FDC, APC, 물류 시스템이 동시에 움직입니다. 이때 E160 영역의 데이터가 애매하면 운영자는 같은 현상을 서로 다른 용어로 부르게 되고, 개발자는 예외 처리를 코드 곳곳에 흩뿌리게 됩니다. 따라서 먼저 표준이 다루는 경계를 정하고, 그 안에서 공통 객체와 상태를 모델링해야 합니다.

학생에게 설명하는 비유 E160를 하나의 교실 규칙이라고 보면 됩니다. 교사가 출석, 과제, 시험을 같은 양식으로 관리해야 학생별 이력을 비교할 수 있듯이, 장비 자동화도 Quality Code, Reason, Validity Window, Consumer Policy 같은 핵심 요소를 같은 언어로 관리해야 합니다.
개발자에게 중요한 이유 표준을 데이터 모델로 옮기면 화면, API, 이벤트 처리, 장애 분석이 같은 기준을 공유합니다. 반대로 표준을 문서로만 두면 프로젝트마다 다른 용어와 상태값이 생겨 유지보수가 어려워집니다.

2. DFD: 데이터가 흘러가는 방식

Raw SampleInput
→
품질 규칙 적용Process
→
Quality Code 부여Process
→
Annotated Data 저장Process
→
소비 시스템 판단Output

위 흐름은 E160를 프로그램으로 구현할 때의 기본 DFD입니다. 단순히 화면에 값을 보여주는 흐름이 아니라, 입력, 검증, 상태 판단, 저장, 업무 시스템 전달까지 포함합니다.

단계처리 의미개발 시 저장/검증 포인트
1. Raw Sample입력 데이터 또는 시작 조건장비, Host, 운영자, 물류 시스템에서 발생
2. 품질 규칙 적용검증, 변환, 상태 판단을 수행하는 처리 단계중간 결과를 로그와 상태 테이블에 남김
3. Quality Code 부여검증, 변환, 상태 판단을 수행하는 처리 단계중간 결과를 로그와 상태 테이블에 남김
4. Annotated Data 저장검증, 변환, 상태 판단을 수행하는 처리 단계중간 결과를 로그와 상태 테이블에 남김
5. 소비 시스템 판단업무 시스템이 사용하는 결과MES/EAP/대시보드/분석 시스템으로 전달

3. 핵심 객체와 상태 모델

E160 구현은 아래 객체들을 중심으로 설계하면 이해가 쉽습니다. 학생들은 각 객체가 "무엇을 식별하고", "어떤 상태를 가지며", "어떤 이벤트로 변하는지"를 먼저 그려보면 됩니다.

객체/개념역할수업식 해설
Quality Code품질 상태Good, Suspect, Bad, Missing, OutOfRange 같은 판단입니다.
Reason품질 사유센서 오류, 통신 지연, calibration 만료 등 원인입니다.
Validity Window유효 시간값이 어느 기간 동안 유효한지 나타냅니다.
Consumer Policy사용 정책품질별로 사용, 보간, 제외, 알람을 결정합니다.

상태 전이 관점

상태 모델은 "현재 상태를 저장하는 테이블"과 "상태가 바뀐 이력 테이블"을 분리해서 생각해야 합니다. 현재 상태는 화면과 제어 판단에 빠르게 쓰이고, 이력은 감사, 추적, KPI 계산, 장애 분석에 쓰입니다.

state_event_received // 장비 상태 이벤트 수신 -> validate_event_order // 이벤트 순서 및 유효성 검증 -> close_previous_interval_if_needed // 이전 구간 마감 처리 (필요시) -> update_current_state // 현재 상태 업데이트 -> append_history // 이력 테이블에 저장 -> publish_business_event // 상위 시스템으로 비즈니스 이벤트 발행

4. 메시지와 이벤트 설계

표준을 실제 시스템에 연결할 때는 메시지 이름보다 메시지가 만드는 업무 효과를 더 중요하게 봐야 합니다. 예를 들어 ACK가 성공이어도 실제 상태가 바뀌지 않았으면 업무적으로는 아직 완료가 아닙니다.

메시지/이벤트의도구현 시 확인할 점
Sample With Quality품질 포함 sample값과 quality code를 함께 전달합니다.
Quality Rule Update규칙 변경품질 판단 기준이 바뀌면 version을 남깁니다.
Quality Issue Event품질 문제 보고결측이나 이상값이 지속될 때 알립니다.

5. 권장 데이터베이스 구조

아래 테이블은 교육용 설계 예시입니다. 실제 프로젝트에서는 장비 수, 이벤트량, 보존 기간, 고객 naming rule에 맞춰 column을 조정해야 합니다. 그래도 핵심은 원본 이벤트, 현재 상태, 이력, 설정 버전을 분리하는 것입니다.

테이블권장 컬럼설계 이유
quality_annotated_samplesample_id, parameter_id, value_text, quality_code, quality_reason, sample_time운영 화면, 이력 추적, 장애 분석, 재처리를 분리하기 위한 기본 저장소입니다.
data_quality_rulerule_id, parameter_id, rule_type, threshold_json, severity, version운영 화면, 이력 추적, 장애 분석, 재처리를 분리하기 위한 기본 저장소입니다.

ERD를 그릴 때의 원칙

  • 장비 ID, 표준 객체 ID, 발생 시각은 대부분의 테이블에 들어가는 기본 축입니다.
  • 현재 상태 테이블은 업데이트가 많고, 이력 테이블은 append 중심으로 설계합니다.
  • 설정값과 사전 정보는 version을 둡니다. 장비 SW 변경 후 같은 ID의 의미가 바뀌는 경우가 있습니다.
  • 원본 payload 또는 raw message 참조를 남기면 장애 분석과 재처리가 쉬워집니다.

6. 구현 절차

처음부터 전체 자동화를 만들려고 하면 복잡합니다. 수업 프로젝트나 PoC에서는 다음 순서로 구현하면 기능이 자연스럽게 쌓입니다.

순서구현 항목완료 기준
1품질 코드는 원본값을 삭제하지 않습니다. 원본값, 품질 판단, 판단 시각을 모두 보존합니다.입력 조건과 설정값이 화면/DB에 남는다.
2AI/통계 계산에서는 품질 코드별 처리 정책을 명시합니다. Bad는 제외, Suspect는 가중치 축소처럼 정합니다.정상/오류 케이스가 테스트로 재현된다.
3시간 지연 품질은 sample_time과 received_at 차이로 계산합니다.정상/오류 케이스가 테스트로 재현된다.
4품질 규칙 변경은 모델 재학습과 KPI 재계산에 영향을 주므로 version을 반드시 남깁니다.장애 상황에서도 로그와 상태가 일관된다.

서비스 분리 예시

Controller/API // 외부 요청 및 이벤트 접수 -> Command Validator // 명령어 형식 및 기본 검증 -> Standard Domain Service (E160) // 표준 비즈니스 로직 및 상태 전이 판단 -> State Repository // 현재 상태 DB 저장 및 조회 -> Event Publisher // 처리 결과 이벤트 발행 -> Audit/Metric Writer // 감사 로그 및 성능 지표 기록

Domain Service 안에는 E160의 상태 전이, 권한 판단, 데이터 품질 판단 같은 표준별 규칙을 넣고, Controller에는 HTTP나 화면 요청 처리만 남기는 구조가 유지보수에 좋습니다.

7. 처리 로직 상세

아래 의사코드는 E160 이벤트를 받았을 때 공통적으로 적용할 수 있는 처리 흐름입니다. 실제 코드는 Java, C#, Python, Node.js 어느 언어로 작성해도 되지만 순서는 유지하는 편이 안전합니다.

function handleE160Event(event): // 표준 이벤트 처리 진입점 assert event.equipmentId is not empty // 설비 식별자 존재 여부 확인 assert event.eventTime is not in the future beyond allowedSkew // 발생 시간이 미래인지(허용 오차 내) 확인 dictionary = loadDictionary(event.equipmentId, event.standardVersion) // 설비별/표준버전별 사전(Dictionary) 로드 normalized = normalize(event, dictionary) // 사전 기반 데이터 정규화 및 표준화 validationResult = validateBusinessRule(normalized) // 표준 비즈니스 룰 기반 유효성 검증 saveRawEvent(event) // 원본 이벤트 로우 데이터 저장 if validationResult.ok: // 검증 통과 시 updateCurrentState(normalized) // 현재 상태 DB 반영 appendHistory(normalized) // 이력 DB에 추가 publishToConsumers(normalized) // 구독 시스템(분석, UI 등)에 데이터 발행 else: // 조건 불만족 시 createExceptionRecord(normalized, validationResult.reason) // 예외 상황 및 실패 사유 기록 notifyOperatorIfNeeded() // 필요 시 작업자에게 알림 발송

예외 처리 원칙

  • 오류 이벤트도 버리지 않습니다. raw event와 실패 이유를 저장해야 재처리와 벤더 문의가 가능합니다.
  • 장비 시간과 서버 시간이 다를 수 있으므로 허용 가능한 clock skew를 설정합니다.
  • 중복 이벤트는 idempotency key로 걸러냅니다. 보통 equipment_id, event_name, event_time, sequence를 조합합니다.
  • 업무 시스템으로 내보내기 전에 표준 상태값을 사내 공통 코드로 매핑합니다.

8. 테스트 시나리오

표준 구현의 품질은 정상 케이스보다 예외 케이스에서 드러납니다. 아래 테스트를 자동화하면 장비 반입과 SW 변경 검증 시간이 크게 줄어듭니다.

테스트입력 조건기대 결과
TC-01범위 초과 sample Bad 처리상태, 이력, 알람 또는 ACK가 설계 문서와 일치해야 합니다.
TC-02결측 구간 Missing 생성상태, 이력, 알람 또는 ACK가 설계 문서와 일치해야 합니다.
TC-03지연 sample Suspect 처리상태, 이력, 알람 또는 ACK가 설계 문서와 일치해야 합니다.
TC-04품질별 KPI 제외 정책 검증상태, 이력, 알람 또는 ACK가 설계 문서와 일치해야 합니다.

자주 발생하는 실수

Bad 값을 null로 덮어써 원인 분석 불가 품질 코드 없이 평균 계산 시간 지연을 결측으로 오판

9. 운영 화면과 모니터링 설계

E160를 운영 시스템에 넣을 때는 개발자 로그만으로 부족합니다. 운영자가 즉시 판단할 수 있도록 현재 상태, 마지막 이벤트 시각, 실패 원인, 관련 객체 링크를 한 화면에 보여줘야 합니다.

상태 패널현재 상태, 마지막 정상 이벤트, 마지막 오류 이벤트, 장비/Client 연결 상태를 표시합니다.
이력 타임라인이벤트가 어떤 순서로 발생했는지 시간축으로 보여주고 raw payload까지 drill-down할 수 있게 합니다.
품질/예외 큐미처리 오류, 재처리 대상, 승인 대기 예외를 운영자가 확인하고 조치합니다.

완료 체크리스트

  • 표준 객체와 사내 공통 코드의 매핑표가 있다.
  • 정상/오류/재처리/중복 이벤트 테스트가 자동화되어 있다.
  • 운영자가 볼 수 있는 현재 상태 화면과 이력 화면이 있다.
  • 장비 SW 또는 표준 사전 변경 시 영향 분석 절차가 있다.
  • 공식 SEMI 문서와 고객 사양서 기준으로 최종 검토했다.
