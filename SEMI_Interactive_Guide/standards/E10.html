수업에서 기억할 핵심: E10는 장비 성능 대시보드, 설비 벤더 평가, PM 효과 분석, 다운타임 Pareto, OEE 계산의 시간 기반 입력으로 사용합니다. 이 문서를 읽을 때는 표준 번호를 외우는 것보다, 입력 데이터가 어디서 오고 어떤 상태 판단을 거쳐 어떤 업무 시스템으로 전달되는지 따라가야 합니다.

1. 표준의 역할과 현장 배경

SEMI E10은 장비 시간을 Productive, Standby, Engineering, Scheduled Downtime, Unscheduled Downtime, Non-Scheduled Time 등으로 나누고 MTBF, MTTR, Availability 같은 지표를 계산하는 방법을 설명합니다.

반도체 fab의 자동화 시스템은 장비, EAP, MES, FDC, APC, 물류 시스템이 동시에 움직입니다. 이때 E10 영역의 데이터가 애매하면 운영자는 같은 현상을 서로 다른 용어로 부르게 되고, 개발자는 예외 처리를 코드 곳곳에 흩뿌리게 됩니다. 따라서 먼저 표준이 다루는 경계를 정하고, 그 안에서 공통 객체와 상태를 모델링해야 합니다.

학생에게 설명하는 비유 E10를 하나의 교실 규칙이라고 보면 됩니다. 교사가 출석, 과제, 시험을 같은 양식으로 관리해야 학생별 이력을 비교할 수 있듯이, 장비 자동화도 PRD, SBY, ENG, SDT 같은 핵심 요소를 같은 언어로 관리해야 합니다.
개발자에게 중요한 이유 표준을 데이터 모델로 옮기면 화면, API, 이벤트 처리, 장애 분석이 같은 기준을 공유합니다. 반대로 표준을 문서로만 두면 프로젝트마다 다른 용어와 상태값이 생겨 유지보수가 어려워집니다.

2. DFD: 데이터가 흘러가는 방식

상태 이벤트 수집Input
→
E10 상태 분류Process
→
시간 구간 보정Process
→
RAM 지표 계산Process
→
Dashboard/ReportOutput

위 흐름은 E10를 프로그램으로 구현할 때의 기본 DFD입니다. 단순히 화면에 값을 보여주는 흐름이 아니라, 입력, 검증, 상태 판단, 저장, 업무 시스템 전달까지 포함합니다.

단계처리 의미개발 시 저장/검증 포인트
1. 상태 이벤트 수집입력 데이터 또는 시작 조건장비, Host, 운영자, 물류 시스템에서 발생
2. E10 상태 분류검증, 변환, 상태 판단을 수행하는 처리 단계중간 결과를 로그와 상태 테이블에 남김
3. 시간 구간 보정검증, 변환, 상태 판단을 수행하는 처리 단계중간 결과를 로그와 상태 테이블에 남김
4. RAM 지표 계산검증, 변환, 상태 판단을 수행하는 처리 단계중간 결과를 로그와 상태 테이블에 남김
5. Dashboard/Report업무 시스템이 사용하는 결과MES/EAP/대시보드/분석 시스템으로 전달

3. 핵심 객체와 상태 모델

E10 구현은 아래 객체들을 중심으로 설계하면 이해가 쉽습니다. 학생들은 각 객체가 "무엇을 식별하고", "어떤 상태를 가지며", "어떤 이벤트로 변하는지"를 먼저 그려보면 됩니다.

객체/개념역할수업식 해설
PRD생산 시간가치 있는 정상 공정 수행 시간입니다.
SBY대기 시간장비는 가능하지만 제품, 작업자, Host 지시 등 외부 사유로 기다리는 시간입니다.
ENG엔지니어링 시간시험, 개선, 조건 조정 등 생산 외 기술 활동 시간입니다.
SDT계획 정지PM, 계획된 setup, 정기 점검처럼 사전에 계획된 정지입니다.
UDT비계획 정지고장, unexpected failure, 수리 대기 등 신뢰성 손실을 나타냅니다.
NST비가동 계획 제외공장 휴무, 설치, 장기 보관처럼 분석 모수에서 제외할 수 있는 시간입니다.

상태 전이 관점

상태 모델은 "현재 상태를 저장하는 테이블"과 "상태가 바뀐 이력 테이블"을 분리해서 생각해야 합니다. 현재 상태는 화면과 제어 판단에 빠르게 쓰이고, 이력은 감사, 추적, KPI 계산, 장애 분석에 쓰입니다.

state_event_received -> validate_event_order -> close_previous_interval_if_needed -> update_current_state -> append_history -> publish_business_event

4. 메시지와 이벤트 설계

표준을 실제 시스템에 연결할 때는 메시지 이름보다 메시지가 만드는 업무 효과를 더 중요하게 봐야 합니다. 예를 들어 ACK가 성공이어도 실제 상태가 바뀌지 않았으면 업무적으로는 아직 완료가 아닙니다.

메시지/이벤트의도구현 시 확인할 점
State Change상태 전이 이벤트시작 시간과 종료 시간을 계산하는 원천입니다.
Reason Code원인 분류다운타임 Pareto와 책임 구분에 사용합니다.
Failure Count고장 횟수MTBF/MTTR 계산의 분모가 됩니다.

5. 권장 데이터베이스 구조

아래 테이블은 교육용 설계 예시입니다. 실제 프로젝트에서는 장비 수, 이벤트량, 보존 기간, 고객 naming rule에 맞춰 column을 조정해야 합니다. 그래도 핵심은 원본 이벤트, 현재 상태, 이력, 설정 버전을 분리하는 것입니다.

테이블권장 컬럼설계 이유
equipment_state_intervalequipment_id, e10_state, reason_code, start_time, end_time, duration_sec, source_event_id운영 화면, 이력 추적, 장애 분석, 재처리를 분리하기 위한 기본 저장소입니다.
availability_metricequipment_id, metric_name, numerator_sec, denominator_sec, value, window_start, window_end운영 화면, 이력 추적, 장애 분석, 재처리를 분리하기 위한 기본 저장소입니다.
downtime_reason_paretoequipment_id, reason_code, downtime_sec, occurrence_count, window_start, window_end운영 화면, 이력 추적, 장애 분석, 재처리를 분리하기 위한 기본 저장소입니다.

ERD를 그릴 때의 원칙

  • 장비 ID, 표준 객체 ID, 발생 시각은 대부분의 테이블에 들어가는 기본 축입니다.
  • 현재 상태 테이블은 업데이트가 많고, 이력 테이블은 append 중심으로 설계합니다.
  • 설정값과 사전 정보는 version을 둡니다. 장비 SW 변경 후 같은 ID의 의미가 바뀌는 경우가 있습니다.
  • 원본 payload 또는 raw message 참조를 남기면 장애 분석과 재처리가 쉬워집니다.

6. 구현 절차

처음부터 전체 자동화를 만들려고 하면 복잡합니다. 수업 프로젝트나 PoC에서는 다음 순서로 구현하면 기능이 자연스럽게 쌓입니다.

순서구현 항목완료 기준
1상태 이벤트를 바로 KPI로 계산하지 말고 먼저 time interval로 정규화합니다. 지연 도착 이벤트와 중복 이벤트를 보정하기 쉽습니다.입력 조건과 설정값이 화면/DB에 남는다.
2한 순간에는 하나의 E10 상태만 존재하도록 우선순위 룰을 둡니다. 예를 들어 UDT가 SBY보다 우선인지 고객과 합의합니다.정상/오류 케이스가 테스트로 재현된다.
3MTBF의 failure count 기준은 assist와 failure를 구분해야 합니다. 짧은 operator assist를 모두 failure로 세면 신뢰성이 과소평가됩니다.정상/오류 케이스가 테스트로 재현된다.
4대시보드에는 지표값뿐 아니라 분자/분모 시간도 같이 표시합니다. Availability 95%가 어떤 모수에서 나온 값인지 알 수 있어야 합니다.장애 상황에서도 로그와 상태가 일관된다.

서비스 분리 예시

Controller/API -> Command Validator -> Standard Domain Service (E10) -> State Repository -> Event Publisher -> Audit/Metric Writer

Domain Service 안에는 E10의 상태 전이, 권한 판단, 데이터 품질 판단 같은 표준별 규칙을 넣고, Controller에는 HTTP나 화면 요청 처리만 남기는 구조가 유지보수에 좋습니다.

7. 처리 로직 상세

아래 의사코드는 E10 이벤트를 받았을 때 공통적으로 적용할 수 있는 처리 흐름입니다. 실제 코드는 Java, C#, Python, Node.js 어느 언어로 작성해도 되지만 순서는 유지하는 편이 안전합니다.

function handleE10Event(event): assert event.equipmentId is not empty assert event.eventTime is not in the future beyond allowedSkew dictionary = loadDictionary(event.equipmentId, event.standardVersion) normalized = normalize(event, dictionary) validationResult = validateBusinessRule(normalized) saveRawEvent(event) if validationResult.ok: updateCurrentState(normalized) appendHistory(normalized) publishToConsumers(normalized) else: createExceptionRecord(normalized, validationResult.reason) notifyOperatorIfNeeded()

예외 처리 원칙

  • 오류 이벤트도 버리지 않습니다. raw event와 실패 이유를 저장해야 재처리와 벤더 문의가 가능합니다.
  • 장비 시간과 서버 시간이 다를 수 있으므로 허용 가능한 clock skew를 설정합니다.
  • 중복 이벤트는 idempotency key로 걸러냅니다. 보통 equipment_id, event_name, event_time, sequence를 조합합니다.
  • 업무 시스템으로 내보내기 전에 표준 상태값을 사내 공통 코드로 매핑합니다.

8. 테스트 시나리오

표준 구현의 품질은 정상 케이스보다 예외 케이스에서 드러납니다. 아래 테스트를 자동화하면 장비 반입과 SW 변경 검증 시간이 크게 줄어듭니다.

테스트입력 조건기대 결과
TC-0124시간 상태 구간 합계 검증상태, 이력, 알람 또는 ACK가 설계 문서와 일치해야 합니다.
TC-02겹친 이벤트 우선순위 적용상태, 이력, 알람 또는 ACK가 설계 문서와 일치해야 합니다.
TC-03MTBF/MTTR 수식 검증상태, 이력, 알람 또는 ACK가 설계 문서와 일치해야 합니다.
TC-04다운타임 Pareto reason code 집계상태, 이력, 알람 또는 ACK가 설계 문서와 일치해야 합니다.

자주 발생하는 실수

상태 겹침 구간을 중복 합산 NST를 denominator에 넣어 설비 효율을 낮게 계산 failure와 assist 미구분 장비 시간대와 MES 시간대 불일치

9. 운영 화면과 모니터링 설계

E10를 운영 시스템에 넣을 때는 개발자 로그만으로 부족합니다. 운영자가 즉시 판단할 수 있도록 현재 상태, 마지막 이벤트 시각, 실패 원인, 관련 객체 링크를 한 화면에 보여줘야 합니다.

상태 패널현재 상태, 마지막 정상 이벤트, 마지막 오류 이벤트, 장비/Client 연결 상태를 표시합니다.
이력 타임라인이벤트가 어떤 순서로 발생했는지 시간축으로 보여주고 raw payload까지 drill-down할 수 있게 합니다.
품질/예외 큐미처리 오류, 재처리 대상, 승인 대기 예외를 운영자가 확인하고 조치합니다.

완료 체크리스트

  • 표준 객체와 사내 공통 코드의 매핑표가 있다.
  • 정상/오류/재처리/중복 이벤트 테스트가 자동화되어 있다.
  • 운영자가 볼 수 있는 현재 상태 화면과 이력 화면이 있다.
  • 장비 SW 또는 표준 사전 변경 시 영향 분석 절차가 있다.
  • 공식 SEMI 문서와 고객 사양서 기준으로 최종 검토했다.
