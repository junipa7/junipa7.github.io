1장. SEMI E5 (SECS-II) 개요 및 핵심 구조

SEMI E5는 SECS-II (SEMI Equipment Communications Standard 2) 표준으로, 장비와 호스트 간에 주고받는 메시지의 "문법과 의미(Semantics)"를 정의합니다. HSMS(E37)나 SECS-I(E4)가 데이터를 배달하는 '트럭과 도로'라면, SECS-II는 트럭에 실린 '상자 안의 내용물(데이터 구조와 명령어)'입니다.

1. Stream과 Function (SxFy) 구조

모든 SECS-II 메시지는 대분류인 Stream과 소분류인 Function으로 나뉘어 고유한 목적을 가집니다.

  • Stream (S): 메시지의 카테고리를 나타냅니다. (예: Stream 1 = 장비 상태, Stream 2 = 장비 제어, Stream 6 = 데이터 수집).
  • Function (F): 해당 카테고리 내의 구체적인 액션입니다. 보통 홀수(Odd)는 요청/송신(Primary Message)을, 짝수(Even)는 응답(Secondary Message)을 의미합니다. (예: S1F1 = Are You There Request, S1F2 = On Line Data).

2. W-Bit (Wait Bit)

메시지 헤더에 포함되는 1비트의 플래그로, 메시지를 전송한 후 상대방의 응답(Reply)을 반드시 기다려야 하는지 여부를 나타냅니다.

W=1이면 응답 대기 (Transaction 형성), W=0이면 응답을 기다리지 않음 (통보성 메시지).

2장. 데이터 타입과 아이템 (Data Types & Items)

SECS-II 메시지는 단순한 문자열이 아니라, 트리(Tree) 구조로 묶인 데이터 아이템들의 집합으로 구성됩니다.

1. 데이터 포맷 코드 (Format Codes)

타입 기호의미활용 예시
L (List)리스트 (하위 요소들의 배열 형태)L, 3 (하위에 3개의 아이템이 있음)
A (ASCII)문자열 데이터레시피 이름, 알람 텍스트, 장비 모델명

2. 데이터 아이템 구조 (Item Format)

각 데이터 아이템은 [포맷 코드(Format) + 길이(Length) + 실제 데이터(Data)]의 바이트 시퀀스로 전송되어, 파서(Parser)가 길이를 읽고 정확하게 데이터를 잘라낼 수 있게 합니다.

3장. 주요 Stream과 Function (SxFy) 심층 분석

수백 개의 SECS-II 메시지 중 실무에서 가장 빈번하게 사용되는 핵심 메시지들을 기능별로 분류합니다.

1. Stream 1: Equipment Status (장비 상태 파악)

  • S1F1 / S1F2 (Are You There): 장비와 호스트 간의 물리적/논리적 연결이 살아있는지 확인하는 통신 핑거(Ping) 테스트.
  • S1F3 / S1F4 (Selected Equipment Status): 호스트가 장비의 특정 SVID(Status Variable ID, 예: 현재 온도, 챔버 압력) 값을 콕 집어서 요청하고 응답받는 메시지.
  • S1F13 / S1F14 (Establish Communications): 물리적 연결(TCP/IP) 후, 논리적인 SECS 통신 세션을 수립하기 위한 첫 번째 악수(Handshake).

2. Stream 2: Equipment Control (장비 제어)

  • S2F13 / S2F14 (Equipment Constant): 장비의 기본 설정 변수(ECV, 예: 타임아웃 기준 시간, 속도 제한)를 조회.
  • S2F15 / S2F16 (New Equipment Constant): 장비의 설정 변수를 호스트에서 변경하도록 지시.
  • S2F41 / S2F42 (Host Command): 호스트가 장비에 직접 명령을 내립니다. (예: START, STOP, PAUSE, ABORT). RCMD라는 인자를 통해 명령의 종류를 구분합니다.

3. Stream 5: Exception Reporting (알람 보고)

  • S5F1 / S5F2 (Alarm Report): 장비 내부에서 에러/알람(ALID)이 발생(Set)하거나 해제(Clear)될 때 즉시 호스트로 쏘아주는 메시지.
  • S5F3 / S5F4 (Enable/Disable Alarm): 호스트가 장비의 특정 알람을 무시하도록(Disable) 하거나 다시 켜도록(Enable) 설정.

4. Stream 6: Data Collection (데이터 수집 및 이벤트)

  • S6F11 / S6F12 (Event Report): SECS-II에서 가장 중요한 메시지입니다. 장비에서 특정 이벤트(CEID, 예: 웨이퍼 반입, 공정 시작, 공정 완료)가 발생하면, 해당 이벤트에 미리 묶어둔 데이터(Report)를 호스트로 전송하여 추적성(Traceability)을 제공합니다.
  • S6F1 / S6F2 (Trace Data): 장비의 센서 값을 1초, 5초 등 정해진 주기마다 호스트로 쏟아내는 실시간 모니터링 데이터 (FDC 시스템의 핵심 소스).

5. Stream 7: Process Program Management (레시피 관리)

  • S7F1 / S7F2 (Process Program Load Inquire): 호스트가 장비에게 레시피 파일을 다운로드하기 전, 장비의 저장 공간이나 상태가 받을 수 있는지 확인 요청.
  • S7F3 / S7F4 (Process Program Send): 실제 레시피 본문 데이터(PPBODY)를 전송. 포맷팅된 ASCII 또는 Binary로 전달됩니다.
  • S7F5 / S7F6 (Process Program Request): 호스트가 장비 내부에 저장된 레시피를 달라고 요청 (레시피 업로드/백업).

6. Stream 9: System Errors (시스템 에러 보고)

S9F1부터 S9F11까지 존재하며, 장비가 호스트로부터 이해할 수 없거나 잘못된 메시지를 받았을 때(예: 정의되지 않은 SxFy 수신, 데이터 포맷 에러, 메시지 길이 불일치, 통신 타임아웃) 에러 내역을 통보합니다.

4장. 실무 적용 및 주의사항 (Implementation)

메시지 사이즈 제한과 분할 전송 수십 MB에 달하는 거대한 레시피나 방대한 Trace 데이터를 한 번에 전송하면 버퍼 오버플로우가 발생할 수 있습니다. 큰 데이터는 Stream 13 (Data Set Transfer)을 사용하거나 여러 블록(Multi-block)으로 분할 전송하는 방식을 사전에 협의해야 합니다.
다이내믹 이벤트 리포팅 (Dynamic Event Report) 모든 센서 데이터를 항상 S6F11로 보내면 네트워크가 다운됩니다. GEM(E30) 표준을 활용하여 호스트가 "이 이벤트(CEID)가 발생할 때만 이 데이터들(Report)을 묶어서 보내라"라고 동적으로 설정(S2F33/S2F35/S2F37)하도록 설계하는 것이 필수입니다.
SECS-II 파서(Parser) 구현 List 안에 List가 무한히 중첩될 수 있는 SECS-II의 트리 구조 특성상, 파서는 반드시 재귀 함수(Recursive function) 형태로 구현되어야 유연하고 에러 없는 데이터 처리가 가능합니다.
